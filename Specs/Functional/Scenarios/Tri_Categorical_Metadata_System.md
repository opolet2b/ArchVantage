# **Functional Specification: Tri-Categorical Metadata System (TCMS)**

## **1\. Concept Overview**

The TCMS is a data-driven framework for "Things" (Nodes) that differentiates between immutable technical data, user-defined properties, and scenario-specific AI insights. It enables the canvas to function as a spatial database where data is visualized directly on the node face and acted upon through automation.

## **2\. The Three Metadata Categories**

### **2.1 Category 1: Technical Metadata (Immutable)**

Extracted automatically by the system upon creation or ingestion.

* **Integrity & Versioning**:  
  * version\_hash: A cryptographic hash (SHA-256) of the content for unique identification and version tracking.  
  * checksum: Standard checksum for monitoring external file integrity.  
* **Standard Fields**: source\_type (File, URL, Note), file\_details (name, size, mime), chronology (created\_at, modified\_at), origin (source path/URL), and owner\_id.

### **2.2 Category 2: Custom Metadata (User/Scenario Defined)**

Business-logic properties defined by the user or enforced by a Scenario.

* **Supported Data Types**:  
  * **Strings/Text**: Alphanumeric fields.  
  * **Numbers**: Integers/floats (can be rendered as progress bars).  
  * **Booleans**: True/False toggles.  
  * **Dates & Time**: Specific timestamps or calendar dates.  
  * **Single-select (Enum)**: One choice from a list (UI: Dropdown/Radio).  
  * **Multi-select**: Multiple choices from a list (UI: Checkboxes/Pills).  
  * **Tag arrays**: Free-form categorical labels.  
  * **Custom Checksums**: User-provided integrity strings.  
* **Configuration**: Defined in the **Metadata Tab** of the Scenario Builder.

### **2.3 Category 3: System/AI Metadata (Scenario-Dependent JSON)**

Dynamic insights generated by AI agents or background processes.

* **Storage**: Managed as a structured JSON object. The internal schema is defined entirely by the active Scenario.  
* **Adaptive Rendering**: Raw JSON is transformed into "nice-to-display" UI cards, progress bars, or formatted lists based on scenario-specific templates.  
* **Examples**: ai\_summary, sentiment\_score, entities\_extracted, compliance\_risk.

## **3\. UI/UX & Pinning Hierarchy**

### **3.1 The Inspector Panel**

* **Trigger**: Accessed via a dedicated **Inspector Icon** located in the toolbar of a selected "Thing".  
* **Placement**: Slides out from the **Right Side** of the workspace.  
* **Tabbed Interface**: Divided into "Technical," "Properties" (Custom), and "Insights" (System).  
* **Pinning Toggles**: Every field features a "Pin" icon with three logic levels:  
  1. **Local Pin**: Displays the field only on the current individual node.  
  2. **Global Pin (Shift+Click)**: Applies visibility to all nodes of the same type\_id on the canvas.  
  3. **Scenario Override**: Specific fields are "Force-Pinned" by the scenario (e.g., Status for all Candidates). These cannot be unpinned while the scenario is active.

### **3.2 Canvas Visuals (The Node "Face")**

Pinned metadata is rendered in specific zones on the node:

* **Top-Right (Status & Flags)**: Single-select/Booleans as colored pills. Stacks horizontally from the right. If \>3 pills are pinned, a **"+N" overflow indicator** appears (expandable on hover).  
* **Bottom-Left (Metrics & Scores)**: Numerical values or AI scores stack vertically.  
* **The Metadata Footer**: One descriptive text field allowed at a time (e.g., "Owner: Alice").  
* **Semantic Zoom**: As the user zooms out, node content (text/images) fades, but **Pinned Metadata** remains visible, turning the node into a high-level "Data Card."

## **4\. Scenario Builder Integration: Metadata Tab**

The Scenario Builder includes a dedicated tab to manage the "Data Dictionary" for a specific use case.

### **4.1 Schema Definition**

* **Field Registry**: Creators define keys, labels, and types for Category 2 metadata.  
* **Enum Management**: Definition of options for single and multi-select fields.  
* **Default Visibility**: Setting which fields are pinned by default upon element creation.

### **4.2 Spatial Enforcement (Domain Logic)**

* **Mandatory Requirements**: Scenarios link metadata keys to **Semantic Domains**.  
* **Logic**: If an element enters "Phase B: Business Architecture," the field process\_owner becomes mandatory. The UI highlights missing mandatory data.

## **5\. Logical Enhancements**

### **5.1 Metadata Inheritance**

Nodes automatically inherit specific metadata values from the **Semantic Domain** they reside in (e.g., security level or project code).

### **5.2 Computed Metadata (Synthesis)**

The system supports cross-node aggregations.

* *Example*: A "System" node displays a Total Cost field which is the computed sum of Cost metadata from all child "Component" nodes linked to it.

### **5.3 Integrity Monitoring**

Background service compares Technical.checksum against the current file state, triggering a visual warning if external tampering or modification is detected.
